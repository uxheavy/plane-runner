# Plane Agent Tooling v1 Evaluation Scenarios

## Status and counting rules

Proposed for verification-manifest approval. These 71 rows are distinct behavioral scenarios. A scenario counts only when its actor, setup, action, product outcome, prevention oracle, expected artifacts, and comparison method are version controlled.

The rows are candidate contracts, not yet qualifying scenarios. They begin counting toward the release minimum only when the referenced fixture manifest, prompt, executable predicates, schemas, configuration, and comparison commands are frozen with immutable digests.

- EV-001 through EV-010 are ten broad-planning fixture variants. Each receives three independent authenticated Hermes runs.
- EV-011 through EV-030 are twenty additional authenticated Hermes trials. Each runs once.
- EV-031 through EV-071 are deterministic release scenarios. They do not increase the required live-trial count unless a future approved manifest assigns them live trials.
- Every live trial must resolve provider `openai-codex` and model `gpt-5.6-luna`.
- Setup failures and post-dispatch model failures remain in the trial ledger.
- Repeating a scenario never creates a new scenario ID.
- All security-critical oracles tolerate zero violations.

### Additional live safety contract

- Actor: the dedicated Plane agent identity, generated TypeScript child, or test operator named by the scenario.
- Setup: the named permission boundary, injected fault, resource limit, replay, or hostile probe against fresh tagged fixtures.
- Steps: exercise the real Hermes, callback, gateway, Plane, and audit path; do not replace enforcement with policy mocks.
- Expected artifacts: transcript, generated code where applicable, traces, structured result, durable state before and after, audit readback, and cleanup record.
- Comparison: executable acceptance and prevention assertions, including no forbidden state, leak, partial effect, or duplicate after failure.
- Negative-probe control: the same TypeScript isolate must execute a harmless computation and one authorized host callback before and after each denial probe; traces must prove the probe ran and failed for the intended policy reason.
- Approval: pending as part of release- and verification-manifest approval.

### Deterministic release contract

- Actor: verifier principal, real MCP client, operator, or injected failure harness named by the scenario.
- Setup: exact integration-lock commits, generated digests, seeded test stack, and scenario-specific configuration.
- Steps: invoke the real contract seam or approved failure-injection seam and inspect authoritative state.
- Expected artifacts: command, exit code, structured logs, contract fixtures, state or API readbacks, traces, and digests.
- Comparison: version-controlled assertions with structured diagnostics; every negative control must fail for its intended reason.
- Approval: pending as part of release- and verification-manifest approval.

## Coverage requirements

- Every row maps to at least one executable verifier case before implementation can be declared complete.
- EV-051 includes every approved operation after the named Plane-specific contract scenarios pass.
- EV-052 includes every relevant Plane permission boundary after the named authorization scenarios pass.
- EV-064 includes every current MCP tool.
- EV-059 through EV-063 include every approved MCP client, transport, and authentication mode.
- EV-071 requires the generated handler-call and SDK method/path-to-operation artifacts; an adapter-class label alone cannot satisfy it.
- Every conjunctive row has separately named executable subcases. Passing one conjunct cannot mark the row complete.
- The live trial ledger contains at least the declared allocations; extra attempts remain in the denominator.
- Every prevention assertion checks durable state after failure, not only the returned error.
- No scenario may substitute model prose, mocks, or a policy-unit result for authoritative real-path evidence where the contract requires a real path.
