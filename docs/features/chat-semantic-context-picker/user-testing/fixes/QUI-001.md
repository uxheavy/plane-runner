# QUI-001 — Top-level validation returned HTTP 500

## Outcome

Fixed and verified on 2026-07-29. Authenticated malformed top-level hydration
payloads now return HTTP 400 JSON validation errors instead of the generic HTTP
500 response. Strict unknown-key rejection remains in place, and unknown key
names supplied by the client are not echoed in the response.

## Root cause

`SemanticContextHydrationSerializer.to_internal_value()` called `_strict_keys()`
before DRF's normal field processing. `_strict_keys()` raised a string-style
`ValidationError`, which DRF coerced to a list.

In DRF 3.15.2, `Serializer.run_validation()` calls `to_internal_value()` before
the `try` block that converts list-style validation details to a non-field error
mapping. `Serializer.is_valid(raise_exception=True)` later accessed
`serializer.errors`; `Serializer.errors` passed that list to `ReturnDict`, which
raised `ValueError`. Plane's exception handler safely hid the exception, but the
ordinary client error consequently became HTTP 500.

The pre-fix routed Quinn run reproduced this for `null`, `{}`, either required
top-level field missing, and unknown top-level keys:

```text
collected 31 items
6 failed, 25 passed in 6.53s
ValueError: dictionary update sequence element #0 has length ...; 2 is required
```

## Fix

The serializer now catches only the top-level strict-key `ValidationError` and
re-raises it under DRF's configured `NON_FIELD_ERRORS_KEY`. The error detail is
therefore a mapping before `Serializer.errors` renders it. `_strict_keys()` also
uses a generic unknown-field message so attacker-controlled key names are not
reflected at any nesting level.

No endpoint exception handling, permission behavior, hydration behavior, or
persona-owned dogfood tests were changed. The existing Quinn routed cases are
the focused regression evidence.
